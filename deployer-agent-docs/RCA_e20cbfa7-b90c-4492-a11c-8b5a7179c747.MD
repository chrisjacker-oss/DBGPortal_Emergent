# RCA — signshop-crm: Cloudflare "invalid/incomplete origin response" on document send

**Job:** a4a73454-5a58-489b-be99-10cf3ed54131
**Deployment:** signshop-crm (`13e7f6e2-…`) · active run `e20cbfa7-b90c-4492-a11c-8b5a7179c747` · tier_2 · cloudflare frontend · cluster deployment-cluster-04
**Scope:** Estimate / Sales Order / Invoice "Send" → UI shows *"The origin web server returned an invalid or incomplete response to Cloudflare."*

## Verdict
NOT a pod crash, OOM, timeout, routing, or missing-secret problem. The backend is healthy and is **deliberately returning HTTP 502** on the send path; Cloudflare renders that origin 502 as the "invalid/incomplete response" page. Two layers cause it: (1) an **app error-mapping bug** that turns a client-actionable email-provider rejection into a 5xx, and (2) the **underlying provider rejection** itself (Resend `undeliverable_recipient`).

## Evidence (production, active run)
Pod/runtime health — ruled out:
- Both replicas `Running`, `ready:true`, `restart_count:0`. No OOMKilled / CrashLoop / exit 137. The single `Startup probe 503` + `FailedScheduling` events were transient during the 20:52 tier_change rollout; pods settled and are serving.
- `GET /api/invoices` → **200**. Routing to the K8s origin works. (`GET /api/` → 404 is expected — no route — not a fault.)

Failing path (runtime logs):
```
httpx  POST https://integrations.emergentagent.com/api/v1/email/send  "HTTP/1.1 422 unknown"
server ERROR  Email send failed: 422 {"error":"Undeliverable recipient","message":"Recipient looks undeliverable and was blocked before sending to protect deliverability. For testing, send to delivered@resend.dev","code":"undeliverable_recipient"}
server WARNING Email to road.mso.repair@us.dsv.com failed: 502: Failed to send email
POST /api/invoices/6acd2ff4097bd7a767c26143/send  HTTP/1.1  502 Bad Gateway   (x2)
```
Historical 429s exist but are NOT the current cause — current failures are 422.

Secrets (names only, live run): `EMERGENT_EMAIL_KEY`, `EMAIL_FROM_NAME`, `EMAIL_REPLY_TO`, `INTEGRATION_PROXY_URL` all present and non-empty. No missing/blank email secret.

## Code path (confirmed by reading production source, `backend/server.py`)
`send_email()` (≈L4848):
```python
except httpx.HTTPStatusError as e:
    logger.error(f"Email send failed: {e.response.status_code} {e.response.text}")
    if e.response.status_code == 429:
        raise HTTPException(status_code=429, detail="Email rate limit reached, please try again shortly")
    raise HTTPException(status_code=502, detail="Failed to send email")   # <-- 422 from provider becomes 502
```
`_send_document()` (≈L5277): when every recipient fails,
```python
raise HTTPException(status_code=502, detail="Could not send to any of the selected recipients")
```
Handlers `send_estimate` / `send_sales_order` / `send_invoice` (L5423–5434) all funnel through `_send_document` → `send_email`, which is why all three document types show the identical symptom.

So: provider returns **422 undeliverable_recipient** → app re-raises **502** → Cloudflare shows the generic origin-failure page instead of a useful message.

## Why preview passed but production failed
Preview's controlled check (HTTP 202 at 2026-10-12 20:56 UTC) sent to a deliverable/test recipient, so the provider accepted it. Production sent to a real customer address (`road.mso.repair@us.dsv.com`) that Resend's deliverability pre-check **blocked** → 422. The provider hint *"For testing, send to delivered@resend.dev"* indicates either a restricted/sandbox sending configuration or a genuinely undeliverable recipient/unverified domain.

## Fixes

### 1. Code (E1 applies in source — `backend/server.py`)
Stop surfacing provider rejections as 5xx so Cloudflare never shows the origin-error page and the user gets an actionable message:
- In `send_email()` (≈L4868): for provider `4xx` (especially `422`), raise a client-side status instead of 502 — e.g. `raise HTTPException(status_code=422, detail=<provider message, e.g. "Recipient address was rejected as undeliverable">)`. Keep the 429 branch. Reserve 502/500 for genuine upstream-unreachable/network errors.
- In `_send_document()` (≈L5277): change the all-recipients-failed case from `status_code=502` to a `4xx` (e.g. `422`/`400`) and include which recipients failed.
- Apply the same treatment to the other send aggregators that hardcode 502 (proofs L6723). Optionally return `200` with a per-recipient `failed[]` summary so a partial send isn't a hard error.
Reproduction note: the 422→502 mapping is confirmed by direct source read. The live provider call could NOT be reproduced in the sandbox (no email secret/integration access there), so the provider-side rejection is diagnosed from production logs, not re-executed.

### 2. User / third-party (email deliverability — provider side)
The actual send failure is Resend rejecting the recipient. The user should verify, in the Emergent email/Resend configuration: the sending key/domain is in production (not test/sandbox) and the sending domain is verified, and confirm the target recipient address is valid/deliverable. `EMERGENT_EMAIL_KEY` is present and non-empty, so this is a provider/deliverability setting, not a missing secret.

## Explicitly ruled out
Pod crash, OOM, CPU throttle, restart loop, image-pull, backend routing, and missing/blank email secrets — none present. No deploy or secret change was made (diagnosis-only request).
